# i18n 与角色状态回归根因及修复报告

日期：2026-07-15

## 结论

- i18n 全量清账成果没有被回滚。当前分支修复前与 `origin/main` 完全一致，三语词典仍各有 13,646 个键，英文、老挝文无中文残留、无占位翻译。
- 本轮阻断来自好业财治理页后续新增的 7 个未显式覆盖 UI 文本，不是原 3,244 条翻译重新丢失。
- 原门禁把“扫描到的中文源文本总数”统一打印成 `findings`，容易被误读为欠账总数。实际上其中 3,244 条均已由带真实英/老翻译的 runtime bridge 覆盖。
- 管理员看到停用角色重新出现是实质性写入缺陷，不是角色迁移回滚：用户详情页先调用全量角色接口，而该接口把每个角色强制写成 `is_visible=true`；随后再调用第二个可见性接口补写。第二次请求失败时错误被前端吞掉，第一次“全启用”结果永久保留。

## 历史证据

1. `c2a20feb fix(i18n): clear global translation coverage debt` 完成三语质量清账并强化覆盖门禁；本轮检查确认成果仍在。
2. `6d8601bd fix(rbac): separate password reset from role conflicts` 正确隔离了密码重置与 SoD 角色冲突，但保留了全量角色保存时 `is_visible=true` 的旧写法，并增加了第二次 `/role-visibility` 请求。
3. 该第二次请求使用 `.catch(() => {})`，失败不会阻止“修改成功”提示，因此形成“当时看似修好，重新登录又回旧角色”的现象。
4. 登录鉴权已经只计算 `is_visible != false` 的有效角色；问题发生在管理端保存链路重新激活数据，而不是 token 计算主动恢复角色。

## 已实施修复

### i18n

- 将好业财治理页新增的 7 处 UI 文本改为显式 `t()` 引用。
- 为中文、英文、老挝文补齐 5 个复用词条。
- 门禁输出改为 `scanned / covered / uncovered / locale_quality`，只把未覆盖文本和翻译质量问题视为发布阻断。
- 当前结果：13,651 个三语键平齐，7,336 个 `t()` 引用全部命中；3,244 条源文本全部有 runtime bridge 真翻译覆盖，未覆盖 0，翻译质量问题 0。

### RBAC

- `/api/users/:id/roles` 现在一次接收并原子持久化 `role_code / is_primary / is_visible`，删除前端第二次补写请求。
- 未知角色、重复角色、多个有效主角色不再被静默忽略，直接拒绝保存。
- 停用角色永远不能保持主角色；缺少有效主角色时，后端选择一个有效角色作为主角色。
- 前端停用当前主角色时即时重选有效主角色，不再显示停用角色星标。
- 单角色切换、旧可见性兼容接口均在事务内修正主角色并递增 `perms_version`。
- `/api/system/users` 旧兼容列表只返回有效角色作为当前角色，避免旧页面把停用角色重新展示成当前角色。
- 新增 CI 原子性门禁，禁止用户详情页重新出现 `/role-visibility` 双请求写法。

## 防复发约束

1. 角色列表、主角色、启停状态必须一次请求、一次事务、一次 `perms_version` 更新。
2. 禁止“先默认启用全部角色，再异步补状态”。
3. 禁止吞掉角色保存错误并继续显示成功。
4. i18n 报告必须区分已覆盖源文本和真实未覆盖文本，不再用总扫描数冒充欠账数。
5. 后续新增 UI 文本必须让 `uncovered=0` 后才能发布。
