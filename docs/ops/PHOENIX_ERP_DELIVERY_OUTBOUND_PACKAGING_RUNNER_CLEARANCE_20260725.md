## 业务问题

### BUG-20260725-0001 销售配送单创建异常

- 根因：创建配送单时，订单查询已把 `SO-*` 单号解析为数据库 ID，但后续状态推进仍使用原始输入 `soIds`。以订单号创建时数组为空，配送单虽可创建，销售订单无法进入 `ALLOCATED`。
- 修复：统一使用已解析订单的真实 ID 更新销售订单状态。
- 验证：配送服务测试覆盖 `SO-*` 输入并断言实际订单 ID 被推进。

### BUG-20260724-0004 出库与库存未联动

- 根因：通用 CRUD 可以直接把 `wms_outbound.status` 改为 `DONE`，绕过 WMS 库存扣减和 `inv_ledger` 流水。
- 修复：
  - 新增独立出库确认事务；
  - 锁定出库单并校验状态、仓库范围和可用库存；
  - 支持指定批次或 FIFO 扣减；
  - 库存扣减、流水写入、单据完成保持同一事务；
  - 通用 CRUD 的直接 `DONE` 更新改走 WMS 受控服务；
  - 前端补充批次选择与“确认出库”，完成单禁止再次编辑。
- 失败边界：库存不足时事务失败，单据不得进入 `DONE`。

### BUG-20260722-0003 包装入库后重新进入仍显示未入库

- 根因：
  - 终端页面只依赖浏览器 `localStorage` 判断是否入库；
  - 后端先写交接记录、后生成库存，库存失败时仍可能留下成功表象；
  - 页面重进没有从服务端核对交接和库存双证据。
- 修复：
  - 新增包装入库状态查询；
  - 状态按交接记录和库存批次计算为 `PENDING`、`HANDOVER_ONLY`、`INVENTORY_ONLY`、`COMMITTED`；
  - 仅 `COMMITTED` 显示完成；
  - 确认入库改为先形成库存证据，再写交接记录；
  - 重进页面自动读取服务端状态，部分成功状态 fail-closed 并提示处理。

## Runner HOLD 根因

生产快照共跟踪 14 个未关闭报告，实际 `HOLD` 为 2 个：

1. `BUG-20260717-0001`：A3 已验证采购订单计数修复，但 A4 在落后主线的旧工作树中把“现有修复已正确、待外部发布验证”错误结论为 `HOLD`，A1 随后被依赖链阻塞。
2. `BUG-20260716-0002`：A3 子进程退出后只有未提交报告，没有实现证据；严格证据门禁正确拒绝合并，A1 被依赖链阻塞。

平台根因：

- A3/A4 专用工作树已与 `origin/main` 分叉；原判断只识别“严格落后”，没有识别分叉。
- Runner 与正在开发的 Orchestrator 工作树共用根目录，审计提交会与人工业务改动争抢基线。
- 历史 stderr 曾出现 V8 超长字符串错误；当前进程已恢复，但失败分类器仍可能序列化完整嵌套对象。
- 自动发布开关关闭时，已验证提交会积压在本地，后续 Agent 又从旧 `origin/main` 执行。

## Runner 修复

- 分叉和落后的 Agent 工作树都必须在执行前同步 `origin/main`。
- 失败分类只序列化有界深度、键数、数组项和字符串长度的诊断摘要。
- 最大诊断文本严格限制为 32 KiB，循环引用和超大数组安全截断。
- 保留严格证据门禁：无实现提交、无专项报告或显式 `HOLD` 均不得合并或标记已解决。
