# 出库/领用保存 HTTP 400 闭环（2026-08-26）

## 1. 生产取证

- 生产只读审计 run `32948812743`：checkout revision `9d15d654725fcfc15bd36142e13afd59d15a9dc7`；最近 1 小时 `sys_error_logs` 共 4 条 4xx、0 条 5xx、涉及 2 个路径。
- `sys_error_logs` 的现有摘要 workflow 只输出计数，未输出 group 与请求体，不能仅凭这 4 条记录断言均为本案。为补齐证据，新增 `Outbound 400 Production Evidence` workflow：只读拉取 `/outbound/standalone` 的 400 日志明细，并发送一个必定在事务前失败的非法 payload，确认生产响应结构；不插入单据。
- 生产 schema 只读盘点确认：`wms_outbound` 的去向细分列齐全；`wms_stocktake` 缺页面已提交的库区、货位、批次、附件等列；`wms_transfer` 缺页面已提交的货位、批次、附件、经办人列。

## 2. 根因

本案由两个缺陷叠加造成：

1. `INV_OUTBOUND_DEST_TYPE` 是全局字典，页面对所有出库类型展示全部去向；后端 policy 却按业务类型限制值域。例如 `SALE` 只允许 `CUSTOMER/STORE`，`PRODUCTION_USE` 只允许 `HOUSE/DEPARTMENT/PROJECT`。页面能构造后端必拒的 payload。
2. 后端按约定返回 `{ code: 400, msg: "出库业务校验失败", errors: [...] }`，但共用 `api-client` 只读取 `message`，既忽略 `msg` 又丢弃 `errors[]`，最终固定显示“请求失败 (HTTP 400)”。

这条链路由 `2752acaa`（2026-07-27）引入，policy 由 `7451141b`（2026-07-28）补全；最近 30 天没有修改 standalone 出库链路的回归提交。2026-08-26 的仓库域过滤提交未改变 policy、页面字段或保存 API，因此不是本案引入点。

## 3. 修复

- 共用 `api-client` 同时识别 `message`、`msg`、`errors[]`；`ApiError.errors` 和全局 `api-error` 事件均保留逐条错误，展示格式为“业务校验失败：错误1；错误2”。
- 出库/领用页按 type 过滤去向字典，提交前校验去向值域、数量 `> 0` 且最多 3 位小数、销售 SKU/领用物料口径。
- `CrudForm` 增加通用的依赖字段值域和自定义校验能力；`DictSelect` 增加允许值过滤。
- 调拨改走共用 client，完整透出结构化错误，并把页面元数据写入原子事务单据。
- 盘点/报损审批不再用 generic CRUD 直接改 `APPROVED`，统一调用 `inventory/stocktake/approve` 与 `inventory/loss/approve`；存在盘点差异或报损时批次必填。
- TS 迁移补齐页面/事务确实使用而生产缺失的 WMS 单据列，含幂等 `up()` 与可回滚 `down()`。
