## 2. 执行器安全边界

- 脚本：`scripts/ops/chanjet-shareholder-subject-name-write-gate.mjs`
- 默认只做 dry-run。
- 真实执行必须携带本 Gate 的显式批准 token。
- 目标固定为上述五条，不接受任意账套、科目或名称参数。
- 每次写入前检查 ERP 正式股东、源端当前名称、ACTIVE 末级非预置科目和结构指纹。
- 写入后同时读取两个官方科目接口；两个读端都显示目标名称才算成功。
- 任一读回不一致立即停止，并发出补偿请求。
- 不开放现有通用 `/api/chanjet/call` 的写能力。

## 3. 实际实验结果

只对第一条 `COMP-LAO-AGRI / 400101 / 赵总 -> 赵永伟` 进行了单条 canary。为排除请求体差异，按官方文档验证了顶层 ID、普通科目字段和最小必填字段的合法组合。

每次好业财均返回：

```json
{"result": true}
```

但连续读回结果为：

| 读回接口 | 期望 | 实际 |
|---|---|---|
| `getInitBalanceLists/{bookid}` | 赵永伟 | 赵总 |
| `getInitBalanceList/{bookid}` | 赵永伟 | 赵总 |

因此 `result:true` 只能证明好业财网关接受了请求，不能证明科目已持久化。执行器正确判定为 HOLD，没有继续处理另外四条。

## 5. 根因判断

已排除：

1. 账套或科目编码错误。
2. 当前名称与 ERP 核准名称映射错误。
3. openToken 失效或 HTTP 调用失败。
4. 读取缓存只影响单一接口，因为两个官方读取接口均返回原值。
5. ERP 或执行器把返回值误判成成功；本 Gate 以读回为准。

当前证据指向好业财侧“修改科目”接口的无效果成功响应，可能涉及应用写权限、操作员数据权限或供应商接口实现。仅凭 `result:true` 无法进一步区分，必须由好业财开放平台确认该 appKey / operator / bookId 是否具备科目修改权限，并提供该请求的服务端处理记录。

## 6. A2 / A1 结论

- A2：`PASS WITH CONDITIONS`。精确 allowlist、双读回、补偿、审计和停止规则有效；在供应商权限契约确认前禁止继续四条批量写入。
- A1：`PASS WITH CONDITIONS`。脚本语法通过，dry-run 五条匹配，双读取端一致，最终源数据无残留变化；外部接口业务成功语义仍为阻断项。

## 7. 下一 Gate

`CHANJET_PROVIDER_SUBJECT_UPDATE_PERMISSION_CONTRACT_REVIEW`

需要核准：

1. 当前好业财应用是否单独拥有“修改科目”开放接口权限。
2. openToken 对应操作员在两个账套中是否有科目编辑权限。
3. 好业财是否能按调用时间和账套/科目定位服务端请求日志。
4. 接口是否异步处理，以及官方可依赖的持久化回执或查询端点。

在以上证据就绪前，另外四条保持未写状态，ERP 继续使用已核准的映射名称展示，不伪称好业财源名称已改。
