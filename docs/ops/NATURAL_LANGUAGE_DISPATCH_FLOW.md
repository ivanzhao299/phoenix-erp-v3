# Natural Language Dispatch Flow

> Purpose: define how Codex-Orchestrator turns a user request into structured requirements, Agent tasks, acceptance criteria, and board updates.

## 1. User Natural Language Input

The user may provide a request in plain language, screenshots, copied errors, business context, or a desired outcome. Codex-Orchestrator must preserve the original wording as `Source natural language` before transforming it.

Recommended intake fields:

| Field | Meaning |
| --- | --- |
| Request ID | Stable ID such as `ADF-NL-YYYYMMDD-NN` |
| Source natural language | Original user request |
| Business goal | What user wants to achieve |
| Impact area | UI / API / data / security / finance / deployment / docs |
| Deadline or release target | Optional |
| Explicit constraints | Files, branches, forbidden areas, approval rules |

## 2. Clarity Check

Codex-Orchestrator judges a request as clear only when these items are known:

1. Desired outcome is observable.
2. Impact area is identifiable.
3. Forbidden scope is not contradicted by requested work.
4. Required Agent can be selected from the routing rules.
5. Acceptance criteria can be written without guessing business policy.

## 3. When To Ask Follow-Up Questions

Must ask the user before dispatch when:

1. The request could change auth, permissions, finance, master data, third-party sync, schema, migration, deployment, or production behavior.
2. The target module, company, environment, or user role is ambiguous.
3. The user asks to "fix everything" without a failing evidence boundary.
4. The requested action conflicts with freeze rules or branch/worktree rules.
5. The acceptance result cannot be measured from code, tests, smoke, screenshots, logs, or a report.

Ask at most three short questions. If the request is blocked by policy, stop and explain the blocker instead of dispatching.

## 4. When To Generate A Requirement Directly

Codex-Orchestrator may generate a structured requirement without follow-up when:

1. The task is docs-only, template-only, or isolated low-risk UI copy.
2. The allowed files are explicitly listed.
3. The risk level is L0-L2 and no freeze item is nearby.
4. The user has supplied enough expected output and verification criteria.

## 5. Natural Language To Structured Requirement

Use this transformation:

| Structured field | Source |
| --- | --- |
| Request ID | Generated by Orchestrator |
| Summary | One-sentence outcome |
| Background | User context and evidence |
| In scope | Files, modules, pages, commands allowed |
| Out of scope | Freeze items and explicitly forbidden work |
| Risk level | L0-L5 classification |
| Agents | Routing result |
| Acceptance criteria | Criteria from library plus request-specific checks |
| Required approvals | Human gates required before code, deploy, migration, or production |
| Output artifacts | Report, PR, screenshots, logs, task board update |

## 6. Risk Levels L0-L5

| Level | Meaning | Examples |
| --- | --- | --- |
| L0 | No-code coordination | Status update, task board update, read-only audit |
| L1 | Docs or isolated copy | Templates, runbooks, low-risk text |
| L2 | Low-risk UI or test change | Non-sensitive page display, CSS, small smoke test |
| L3 | Product behavior or security-adjacent | Login, menu, RBAC read path, external API diagnostics, finance display |
| L4 | Data shape, master data, migration-adjacent, deploy-adjacent | Schema/entity/migration request, master data baseline, staging deploy runbook |
| L5 | Production, irreversible, security bypass, financial correctness risk | Production deploy, rollback, data repair, auth bypass, accounting mutation |

Risk is monotonic: if any trigger indicates a higher level, use the higher level.

## 7. Auto-Development Decision

| Risk | Auto-code allowed | Human approval |
| --- | --- | --- |
| L0 | No code | Not required unless policy changes |
| L1 | Yes inside docs/templates | Usually not required |
| L2 | Yes inside approved UI/test scope | Required if touching finance/security/master data page |
| L3 | Limited; prefer task contracts and tests first | Required before behavior changes |
| L4 | No by default | Required before migration/schema/data/deploy work |
| L5 | No | Required; often GO/NO-GO gate |

During W5-RESUME-LIMITED, docs/process automation may proceed; A1 runtime/security blockers are examples only unless explicitly assigned later.

## 8. Agent Selection

1. Start with keyword routing in `AGENT_ROUTING_RULES.md`.
2. Add A1 when build, CI, runtime, test, or startup evidence is required.
3. Add A2 when auth, permissions, token, SSE security, logs, or external interface security appears.
4. Add A3 when backend behavior or critical API path appears.
5. Add A4 when a page, UI path, screenshot, or UAT smoke is required.
6. Add A5 when master data, baseline, data integrity, or gray data appears.
7. Add A6 when staging, deploy, rollback, environment, or server runbook appears.
8. Add A7 when final acceptance, release recommendation, or GO/NO-GO is required.
9. Keep Codex-Orchestrator as owner for intake, splitting, board state, PR synthesis, and final decision.

## 9. Agent Task Contract Generation

For each Agent, generate a contract with:

| Field | Required |
| --- | --- |
| Request ID | Yes |
| Source natural language | Yes |
| Structured requirement | Yes |
| Risk level | Yes |
| Assigned Agent | Yes |
| Allowed files | Yes |
| Forbidden files | Yes |
| Required checks | Yes |
| Acceptance criteria | Yes |
| Rollback plan | Yes |
| Human approval required | Yes |
| Auto-code allowed | Yes |
| Output file | Yes |
| PR rule | Yes |

## 10. Acceptance Criteria Generation

Generate criteria from three layers:

1. Global gates: no frozen item, no forbidden files, branch/worktree correct, status clean before start.
2. Domain gates: use `ACCEPTANCE_CRITERIA_LIBRARY.md` for security, data, UI, CI, deploy, rollback, and docs.
3. Request-specific gates: exact user-visible result, expected report, command output, screenshot, or PR evidence.

## 11. Task Board Update

Codex-Orchestrator updates `AGENT_TASK_BOARD.md` with:

1. One row per dispatched Agent task.
2. Risk level and frozen item status.
3. Output artifact path.
4. Current status: `TODO`, `IN_PROGRESS`, `REVIEW`, `PASS`, `FAIL`, `PASS_WITH_CI_CONDITIONS`, `HOLD`, or `ROLLBACK`.
5. Next action and owner.

## 12. Waiting For Agent Reports

After dispatch:

1. Do not assume completion without the Agent report or PR.
2. Keep blocked tasks in `HOLD` or `BLOCKED` with owner and required decision.
3. Treat missing CI, missing screenshots, missing logs, or unverified smoke as pending evidence.
4. Do not launch downstream Agents unless the board says they are ready and the user has approved activation.

## 13. PR And Report Synthesis

Codex-Orchestrator collects:

1. Changed file list per Agent.
2. Commit hash and PR link when available.
3. Verification evidence and failed checks.
4. Freeze item declaration.
5. Open blockers and rollback plan.

The final synthesis must separate fixed items, unverified items, and known failures.

## 14. Final Decision

Use these outcomes:

| Decision | Meaning |
| --- | --- |
| GO | All required gates passed and no unresolved release blocker remains. |
| GO WITH CONDITIONS | Core gates passed; explicitly listed external/CI/manual evidence remains. |
| HOLD | Release or dispatch must stop pending fix, evidence, or human decision. |
| ROLLBACK | Current change should be reverted or previous release restored. |

A1-CI-Runtime-Gate `FAIL` is currently a sample input for this flow. It must not be fixed inside Phase 2 unless a later user instruction starts the relevant Agent task.
